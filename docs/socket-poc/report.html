02 / 08

Варианты запуска в pull request

Вариант A Manifest scan

CLI рекурсивно выбирает поддерживаемые build descriptors и lockfiles. В фактическом скане это package.json и yarn.lock. Список этих файлов в команде не задан. Зависимости приложения не устанавливаются, yarn build и Docker build не запускаются. Устанавливается только закреплённый CLI в отдельный временный каталог.

Precomputed reachability использует анализ вызовов внутри зависимостей. Исходники приложения ему не нужны. Ограничения включают прямые, приватные и не объявленные в manifest зависимости. Unknown или неподдерживаемый анализ не равен доказанной неприменимости.

Вариант B Full application reachability

socket scan create --reach запускает анализ на GitHub runner. Engine может загружать анализаторы и зависимости; требования к package manager и toolchain зависят от языка. Это не команда универсальной production сборки. В нашем workflow нет явных yarn build или docker build. Мы не утверждаем по одному факту успешного скана, что внутри engine не было подготовительных команд.

У compiled ecosystems могут потребоваться build scripts, разрешение зависимостей или операции компиляции. Для JS/TS цель этого режима — построение модели вызовов приложения и зависимостей, а не выпуск Next.js bundle.

Документация допускает сохранение исходников на своём runner. В Socket передаются результаты анализа, содержащие metadata: в нашем ответе API присутствуют имена файлов приложения и позиции вызовов. Это нужно учитывать при оценке границы данных. Managed scans на стороне Socket — отдельный вариант, в этом POC он не использован.

Исключения Native и центральный VEX

Нативный механизм Socket

Socket resolutions задают scope по repository, ecosystem/package/version и finding. Подходящий resolution применяется перед policy. Преимущество — нативный dashboard и серверные действия. Недостаток для организации — отдельный механизм рядом с исключениями Trivy, Docker и остальных scanner-ов.

Проверка APIФактический результатЧто это подтверждает
listHTTP 403API недоступен текущему токену; причина 403 требует проверки scopes, квоты и доступности функции
create_dry_runHTTP 403API недоступен текущему токену; причина 403 требует проверки scopes, квоты и доступности функции

Ни одного resolution не создано или удалено. Для сквозного теста нужны отдельный repo-scoped token и операции list/create/delete, а для чтения конкретной записи — read. Сценарий: исходная находка → узкий resolution → обновление серверного snapshot/rescan → действие и verdict → отзыв → повторное появление. Dry-run даже при HTTP 200 не заменяет этот сценарий.

Центральный реестр и OpenVEX

Обёртка сначала получает законченный scan, затем применяет решения и лишь после этого выдаёт финальный exit code. Ошибки scanner/API не становятся исключениями. Создание скана выполняется без native CLI --report, поэтому локальный policy report не успевает преждевременно остановить проверку.

VEX подходит для применимости уязвимостей. Принятие риска со сроком действия, исключения лицензий, malware или IaC требуют более общей модели решений. Нельзя кодировать «риск принят» как ложное not_affected.

Отображение в Socket dashboardНативноеБез sync исходная находка остаётся

Текущий статус POCAPI 403; применение не провереноCLI replay проходит; production не включён

Если собственное affected должно отменять также серверное понижение по reachability, нужна явно заданная центральная политика действий. Текущий POC adapter сохраняет server action для affected и только предотвращает более низкоприоритетное VEX-подавление. Он не восстанавливает скрытые native resolutions и не является полноценным policy engine.

Live применение подходящих записей Docker DHI и Aqua к продукту пока не проверено. Voting использует node:20-alpine, собственный feed описывает Debian/DHI Python. Совпадения только CVE недостаточно. Нужны отдельный DHI image test и утверждение, соответствующее конкретному продукту.

POC adapter поддерживает OpenVEX 0.2, точные npm PURL и ограниченный product/subcomponent scope. Qualifiers и subpaths без соответствующих данных не матчятся. Поддержаны CVE/GHSA aliases, приоритет, SHA-256 provenance, конфликтующие статусы и optional organization extension x-poc-expires. Последнее не является стандартным полем OpenVEX.

В обычный PR gate VEX-фильтрация не включена. Для production нужны trusted central configuration, утверждённые решения, проверка подписи/происхождения feed и полный контракт на product identity. Непроверенный PR не должен иметь возможности добавить себе исключение.

Лог шага и закрепление инструмента

Раньше CLI stdout/stderr перенаправлялись в файлы, а обработчик писал находки только в Actions Summary и artifact. Поэтому при раскрытии шага списка уязвимостей не было. Теперь шаг Evaluate server actions and write Summary выводит каждую Block/Warn находку: пакет, версию, CVE/GHSA, severity, server action и исправленную версию.

Monitor/Ignore остаются в JSON, чтобы сохранить доказательства и не переполнять основной лог. Секрет, advisory descriptions и raw HTTP bodies в этот вывод не добавляются.

npm проверяет загружаемые пакеты по integrity lockfile; изменение одного байта lockfile отклоняется до установки. Файлы инструмента хранятся под именами package.manifest и dependencies.lock, затем копируются во временный каталог как обычные npm manifests. Инвентарь приложения в тестах остался 1433 компонента.

Full reachability engine дополнительно загружается механизмом Socket CLI. Проверка top-level CLI и npm dependencies сама по себе не является аудитом всех скачиваемых engine/analyzer binaries. Их версию и vendor integrity следует отдельно зафиксировать для требований полностью воспроизводимой analysis toolchain.

Предлагаемая конфигурация

По умолчанию в PR: manifest scan, generic discovery, server-action gate, читаемый step log, Summary и JSON artifact. Для критичных репозиториев: отдельный opt-in full application reachability; для Voting режим уже прошёл реальный тест. Не включать автоматически полноразмерный анализ во все проекты до измерения времени и подготовки зависимостей.

Для организации: центральный защищённый реестр решений и один reusable evaluator. OpenVEX для vulnerability applicability, отдельная модель для accepted risk и остальных типов исключений. Native Socket resolutions можно синхронизировать из этого реестра для dashboard, сохраняя один источник истины.

Текущий выбор — архитектурная рекомендация после ограниченного POC, а не утверждение, что production exclusion management уже готов. Полный native тест заблокирован 403, VEX adapter ограничен npm, live Docker/Aqua соответствия и release gate ещё не проверены.

Следующие обязательные проверки

  1. Выдать отдельный repo-scoped resolution test token и выполнить создание, применение на серверном snapshot, отзыв и повторный scan.
  2. Добавить одно утверждённое собственное решение для реально применимого npm finding, с владельцем и сроком пересмотра. Не переносить synthetic fixture в central feed.
  3. Подключить trusted central snapshot перед финальным verdict и проверить, что новый PR не может сам себе выдать исключение.
  4. На отдельном DHI image проверить live Docker/Aqua inputs и конфликты с own feed.
  5. В release использовать уже выполняемую Docker build, создать runtime SBOM, сканировать immutable digest и продвигать тот же digest после effective gate.

BuildKit SBOM дополняет исходный npm inventory OS-пакетами и runtime. Для build/dev dependencies сохраняется отдельный контекст. Повторная production сборка ради SCA manifests не нужна. В текущем Dockerfile Voting копируется весь /app после yarn install, поэтому runtime image необходимо проверить отдельно.

Как документировать следующие тесты

Для каждого сценария сохраняем одну запись в test-results.json и связанные evidence. Повторный тест создаёт новую запись с датой и commit; прежний результат не переписывается как доказательство другого запуска.

ПолеЧто записывать
ID и цельНапример EX-N03 — применение и отзыв native resolution
ПредусловияPolicy revision, scopes, repository, mode, runner/toolchain
ВходыGit commit, image digest/platform, scan ID, VEX document hash и source revision
ШагиТочная команда или workflow input, без секретов
Ожидаемый результатEffective action, ожидаемый exit code, ожидаемые изменения UI
Фактический результатПолученный action/exit, числа findings, время; тип evidence
ДоказательстваActions run/job, JSON artifact, фрагмент лога или screenshot с подписью
ВыводPass, fail, blocked или not run; ограничение и следующий шаг
